# M3 handoff: Guardrails, costs, evals

**Goal (PRD):** redaction, rule-based blocking, budget alerts, the Costs, Guardrails and Evals pages,
`lucentpad eval` with a sample GitHub Action. **Done when** demo script steps 3, 4, 5 and 8 work end to end:

4. Ask for a refund over the limit: a rule blocks it, and the block appears as its own span.
5. The agent crosses its budget and an alert fires.
8. Open a PR that breaks a prompt: `lucentpad eval` fails the CI check.

## Step 0: Decisions (user)
| # | Question | Recommendation |
| --- | --- | --- |
| D20 | Where does redaction run? | **At both edges, one shared rule set:** the SDK redacts previews before they leave the process, the gateway before it records a turn, and the ingest API as a last line for anything else. Only what LucentPad **stores** is redacted; requests to the provider are never altered. Built-in detectors: API keys (Anthropic/OpenAI/GitHub/AWS patterns), emails, card numbers (Luhn-checked). Replaced by `[REDACTED:email]` etc. and recorded as a `lucentpad.redaction` event (kind, count), never the value. |
| D21 | Where do blocking rules live and how are they written? | **One YAML file on the server** (`lucentpad.rules.yaml`, path from env), shown read-only on the Guardrails page. Two rule types: **prompt rules** (keywords or regex on the user's message → block before the model is called) and **tool rules** (a condition on a tool's arguments, e.g. `issue_refund.amount > 200` → block before the tool runs). The SDK and gateway fetch rules from the API (`GET /v1/guardrails/rules`) and refresh every 60 s. |
| D22 | What does a block look like to the caller? | **SDK:** raises `lucentpad.GuardrailBlocked` (rule, reason) from the wrapped call or `@span` tool; the demo agent catches it and tells the customer a colleague will follow up. **Gateway:** returns a provider-shaped 400 error naming the rule (Claude Code/Copilot show it as an API error). Both record a `kind="guardrail"` span, `status="blocked"`. |
| D23 | Budgets: who computes spend, and what happens? | **The SDK and gateway estimate spend** from the server's price table (`GET /v1/pricing`, the same table that prices stored spans, so one source of truth). Default **alert**: a `lucentpad.budget.alert` event on the call that crosses it. SDK can opt into a **hard stop** (`trace(..., budget_usd=0.5, on_budget="stop")` → `BudgetExceeded` before the next call). Gateway: per-session budget, **alert only, never stops** (PRD). Defaults: $0.50/SDK run (demo), no default for gateway sessions (env). |
| D24 | Eval cases and checks. | YAML cases in the repo (`evals/*.yaml`): input + checks. **Deterministic checks only** (no LLM judge, in line with the rules-only guardrails): `contains`, `not_contains`, `regex`, `tool_called` (+ args), `no_tool`, `max_cost_usd`, `max_latency_ms`. |
| D25 | What does `lucentpad eval` run against, and how is it kept cheap and honest in CI? | Runs the **real** agent against the **real** model (a prompt change can only be judged by a real model): the demo agent on **Claude Haiku 4.5**, ~6 cases, well under $0.05 per run. CI job runs only when prompts/agent/evals change (path filter), needs an `ANTHROPIC_API_KEY` repo secret, skips cleanly when absent (forks). Baseline = `evals/baseline.json` in the repo (per-case pass/fail + totals), updated with `lucentpad eval --update-baseline`. **Fails** when a case that passed in the baseline now fails, or total cost rises > 25%. Each run is traced and posted to the API for the Evals page. |
| D26 | Costs page content. | Spend over time (stacked by model; switch to client or service), totals for the range, top traces by cost, budget alerts list. Same range picker as Traces. |
| D27 | Guardrails page content. | The active rules (from the YAML), then a live list of blocks and redactions (rule/kind, when, source, trace link), counts per rule for the range. |
| D28 | Demo step 8 needs a PR that breaks a prompt. | I prepare a branch that changes the demo agent's system prompt so it stops using `lookup_order`; you open the PR on GitHub and watch the check fail. Needs the repo secret (D25). |

## Step 1: Contract (lead)
- `schema.py`: `GuardrailRule` (id, type prompt|tool, match, tool, condition, action block, message),
  `GuardrailRules`, `GuardrailEvent` + list (block or redaction, rule/kind, time, trace/span ids, source,
  client), `PriceTable` (per model: input, output, cache read, cache write), `CostSeries` (buckets ×
  group → cost, tokens), `EvalRun`/`EvalCaseResult`/`EvalRunList`. New `Attr`/`EventName` keys:
  `lucentpad.guardrail.reason`, `lucentpad.budget.scope` (run|session), `lucentpad.eval.run_id`,
  `lucentpad.eval.case`.
- Routes: `GET /v1/guardrails/rules`, `GET /v1/guardrails/events?from&to&kind&limit&cursor&since`,
  `GET /v1/pricing`, `GET /v1/costs?from&to&group_by=model|client|service&bucket=auto`,
  `POST /v1/evals/runs`, `GET /v1/evals/runs?limit&cursor`, `GET /v1/evals/runs/{id}`. `make contract`.
- Shared rule/redaction code lives in a small pure module both server and SDK can use: the SDK must not
  depend on the server, so `sdk/lucentpad/guardrails/` holds the engine and the server imports it
  (server depends on `lucentpad-sdk`, not the other way round).

## Step 2: Guardrail engine + redaction (sdk agent) — **Owns:** `sdk/lucentpad/guardrails/`
Pure Python, no I/O: `redact(text) -> (text, [(kind, count)])` with the D20 detectors (Luhn for cards, no
false positives on order numbers or trace ids; tests with tricky near-misses), `load_rules(yaml)`,
`check_prompt(rules, text)`, `check_tool(rules, name, args)` (safe condition evaluator: comparisons on
argument fields, no `eval`). Fast: < 50 µs per 2 kB preview.
**Acceptance:** unit tests incl. adversarial cases; a property test that redaction never leaves a
detected value in the output; benchmark.

## Step 3: Server: rules, pricing, redaction at ingest, gateway enforcement (backend agent) — **Owns:** `server/` except contract files
- Load `LUCENTPAD_RULES_FILE` (default: none → built-in demo rules: refund limit $200); serve rules and
  the price table. Ingest applies `redact` to previews and string attributes as the last line (D20).
- Gateway: prompt rules on the last user message → provider-shaped 400 + guardrail span; redaction before
  recording; per-session budget alert (D23) using `pricing.py`.
- Queries: guardrail events (from guardrail spans + redaction events, indexed), cost series (bucketed
  `date_trunc` over spans with cost; group by model/client/service), eval runs storage (migration: `eval_runs`,
  `eval_cases`) + endpoints.
**Acceptance (real Postgres):** redaction at ingest (email/key/card in previews never stored), gateway
block returns 400 in both provider shapes and records the span, budget alert event on the crossing turn,
cost series sums equal trace totals, events paging, eval run round-trip.

## Step 4: SDK: guardrails + budgets (sdk agent) — **Owns:** `sdk/` except step 2's package
Fetch rules + prices at `init` (background refresh, never blocks the host; if the API is down: built-in
redaction still runs, no rules, budgets from the last known table or off). Prompt rules before each
wrapped call, tool rules in `@span` before the tool body, `GuardrailBlocked`; previews redacted before
export; `trace(budget_usd=, on_budget="alert"|"stop")`, `BudgetExceeded`. Guardrail spans and events per
the span shapes above.
**Acceptance:** block paths for both providers and for tools, redaction of previews incl. streams, budget
alert and stop, API-down behaviour, contract test against `schema.Span`.

## Step 5: Demo agent + eval gate (agent agent) — **Owns:** `examples/`, `evals/`, `.github/workflows/eval.yml` (lead reviews), the `lucentpad eval` CLI in `sdk/lucentpad/cli/`
- Agent: catches `GuardrailBlocked` → hands off politely; budget from config; the customer's email lives in
  the order data so it shows up (redacted) in previews. Mock mode covers steps 3–5 offline.
- `lucentpad eval` (entry point in `lucentpad-sdk`): runs YAML cases against a target command/function,
  checks (D24), compares with the baseline, prints a table, exits non-zero on regression, posts the run.
  `--update-baseline`, `--max-cost`, `--mock` (for tests only).
- `evals/support_agent.yaml` (~6 cases: status question, refund under limit, refund over limit → blocked,
  unknown order, reschedule, no tool for small talk) + `evals/baseline.json`; `.github/workflows/eval.yml`.
**Acceptance:** mock-mode e2e shows steps 3, 4, 5 in one run; eval CLI tests with a fake target (pass,
regression, cost rise, update baseline); workflow lint.

## Step 6: Dashboard: Costs, Guardrails, Evals pages (dashboard agent) — **Owns:** `dashboard/`
Per D26/D27; Evals: runs list (pass/fail, cost, commit, CI link), run detail with per-case results and
diff vs baseline, each case linking to its trace. Load the `dataviz` skill before building the cost
chart. Demo adapter + parity for every new endpoint; sample data gains eval runs.
**Acceptance:** Vitest for each page (range, grouping, live lists, empty states), adapter parity.

## Step 7: Integration + checkpoint (lead + user)
E2E (no real LLM): mock agent run → redacted email in stored previews, guardrail span on the $489 refund,
budget alert event; eval CLI fails on a seeded regression. Then the user: a live run of the agent (real
key) and demo step 8 on GitHub (opens the prepared PR, sees the eval check fail). "approved" → commit
`M3: Guardrails, costs, evals`.
